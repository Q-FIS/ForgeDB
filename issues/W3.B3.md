# [W3.B3] The event loop
labels: week:3, size:M
groups: B

**Size:** M (2-3 days, good for a pair) · **Needs:** W3.B1, W3.B2

## What is this, in plain words?
The main loop of Group B's server: one thread, one `epoll`, thousands of
connections. It's surprisingly short once `Epoll` and `Connection` exist.

## Step by step
In `apps/http_server.cpp`:
1. Make the listening socket non-blocking, and add it to epoll with `EPOLLIN`.
2. Keep the connections in a `std::unordered_map<int, std::unique_ptr<Connection>>` (keyed by fd).
3. Loop: `for (auto& ev : epoll.wait(-1))`:
   - **the listener is ready:** `accept` in a loop until `EAGAIN` (several clients may be waiting). For each one: make it non-blocking, create its `Connection`, and `epoll.add(fd, EPOLLIN)`.
   - **a client is ready:** call `on_readable` or `on_writable`. Then, depending on its new state: `Writing` → `epoll.modify(fd, EPOLLOUT)`; `Reading` → `epoll.modify(fd, EPOLLIN)`; `Closing` → `epoll.remove(fd)` and erase it from the map (the `Socket` destructor closes it).
4. Catch exceptions **per connection**: one broken client is closed and removed; the loop never stops.
5. Delete the week-2 blocking loop (keep it in git history).

## How to test it
`ctest --preset debug -R b_ --output-on-failure`: the week-2 tests must still pass on the new design. Watch it work: `strace -e trace=epoll_wait,accept4,recvfrom,sendto` while you `curl` it.
