# [W3.B5] /sleep, 1,000 connections, and the concurrency tests
labels: week:3, size:S
groups: B

**Size:** S (1 day) · **Needs:** W3.B3

## What is this, in plain words?
Add `/sleep` (a fake slow request), switch on the week-3 tests, and see the
event loop's strength (thousands of idle connections cost almost nothing) and
its weakness (`/sleep` blocks **everyone**).

## Step by step
1. Add `GET /sleep?ms=N` to `routes.cpp`, exactly as in Group A's W3.A3: N from 0 to 10,000, sleep, 200.
2. In `tests/CMakeLists.txt`, uncomment `b_concurrency` and `b_many_connections`. Make them pass on `debug` and `tsan`.
3. **See the weakness:** start your server; in one terminal run `curl 'localhost:8080/sleep?ms=3000'`; in another, run `time curl localhost:8080/health` straight away. Why does `/health` take 3 seconds? Write the answer in `docs/b-week3-notes.md`. This is exactly why the final service (weeks 5-8) adds a worker pool behind the event loop.
4. Load test the release build with `wrk`, as in Group A's W3.A5, at 10, 100 and 1,000 connections, and add the table to the same notes.
