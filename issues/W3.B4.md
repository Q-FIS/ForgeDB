# [W3.B4] Partial writes and big responses
labels: week:3, size:S
groups: B

**Size:** S (1 day) · **Needs:** W3.B3

## What is this, in plain words?
A non-blocking `send` only accepts what fits in the kernel's socket buffer right
now: maybe 200 KB of a 1 MB response. The rest must wait until epoll says the
socket is writable again (`EPOLLOUT`). Get this wrong and big responses arrive
cut short, and nothing crashes, so the bug goes unnoticed. You prove it works.

## Step by step
1. Check that `on_writable` keeps an offset into the output buffer, and continues from it on the next call.
2. Add a big file to the static root for testing (generate a 5 MB file in the test itself; don't commit it), and download it with `curl -o /dev/null -w '%{size_download}'`.
3. Make the receiver slow: a Python client that reads 1 KB every 10 ms. While it downloads, other clients' `/health` must still answer instantly: the slow reader must not block the loop.
4. Add both as unit tests or a small Python test in your group's folder.

## Done when
- [ ] A 5 MB file arrives complete
- [ ] A slow reader doesn't slow down other clients (show the timing in the PR)
