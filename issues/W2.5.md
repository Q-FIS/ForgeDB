# [W2.5] Fuzz it harder, and write down what broke
labels: week:2, size:S
groups: A, B

**Size:** S (1 day) · **Needs:** W2.4

## What is this, in plain words?
The fuzz test in CI sends 3,000 broken requests. You go further: run it much
longer, with sanitizers on, and also with a real fuzzer built into the compiler
(**libFuzzer**). It calls your parser millions of times with inputs it invents
and mutates, looking for crashes. Then write down every bug it found. Finding
your own bugs before an attacker does is the point.

## Step by step
1. Run the black-box fuzzer for longer, on the debug build:
   `python3 tests/http_fuzz.py build/debug/group-a/a_http_server 100000`
2. **libFuzzer** on the parser (needs clang). Create `fuzz/fuzz_parser.cpp` in your group's folder:
   ```cpp
   extern "C" int LLVMFuzzerTestOneInput(const uint8_t* data, size_t size) {
       std::string_view input(reinterpret_cast<const char*>(data), size);
       (void)parse_request_head(input);
       return 0;
   }
   ```
   Build it by hand, in a scratch folder:
   `clang++ -std=c++20 -g -fsanitize=fuzzer,address,undefined -I group-a/src fuzz/fuzz_parser.cpp group-a/src/http_request.cpp -o fuzz_parser && ./fuzz_parser -max_total_time=300`
3. Fix whatever they find, and add each crashing input as a unit test.
4. Write `docs/<group>-week2-fuzzing.md`: what you ran, for how long, every bug found, and the fix.

## Done when
- [ ] 100,000 black-box requests and 5 minutes of libFuzzer, with no crash left
- [ ] Every bug found has a unit test and a line in the notes
